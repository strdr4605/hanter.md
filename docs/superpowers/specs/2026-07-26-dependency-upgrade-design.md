# Dependency Upgrade Design

## Goal

Upgrade every direct npm dependency and GitHub Actions dependency to its latest stable release, adopt the minimum Node.js runtime required by Astro 7, migrate affected project configuration or source code, and leave the production build working.

## Scope

### npm dependencies

| Package | Current | Target |
| --- | --- | --- |
| `@astrojs/svelte` | `7.2.5` | `9.0.1` |
| `@tailwindcss/vite` | `4.2.1` | `4.3.3` |
| `@tinacms/cli` | `2.1.9` | `2.5.6` |
| `astro` | `5.18.0` | `7.1.3` |
| `svelte` | `5.53.7` | `5.56.8` |
| `tailwindcss` | `4.2.1` | `4.3.3` |
| `tinacms` | `3.6.1` | `3.11.0` |

The existing dependency grouping and caret-range convention remain unchanged. `package-lock.json` will be regenerated by npm and remain lockfile version 3.

### Runtime and CI

- Add `engines.node` with `>=22.12.0` because Astro 7 requires Node.js 22.12 or newer.
- Change the GitHub Pages workflow from Node.js 20 to Node.js 22.
- Update action major references:
  - `actions/checkout`: v4 to v7
  - `actions/setup-node`: v4 to v7
  - `actions/configure-pages`: v5 to v6
  - `actions/upload-pages-artifact`: v3 to v5
  - `actions/deploy-pages`: v4 to v5

## Upgrade Method

Use a single-shot upgrade as requested:

1. Record baseline install and build behavior before changing versions.
2. Update all direct npm dependency ranges, Node.js requirements, and GitHub Actions references together.
3. Run npm once to resolve a fresh lockfile for the complete target set.
4. Diagnose resulting install or build failures and apply only required Astro, Svelte, TinaCMS, or Tailwind migrations.
5. Keep unrelated source, content, formatting, and dependency classification unchanged.

## Compatibility Handling

- Upgrade `astro`, `@astrojs/svelte`, and `svelte` as one compatible set.
- Preserve static output, locale routing, Svelte integration, Tailwind Vite integration, and the `/hanter.md` base path.
- Preserve TinaCMS schema and build behavior. Keep generated Tina changes only when the upgraded toolchain requires them.
- Preserve GitHub Pages deployment behavior and Tina environment-variable wiring.
- Do not add validation packages or refactor application code unless an upgrade requires it.

If npm reports a peer conflict, resolve it using versions compatible with all latest direct dependencies rather than downgrading a requested direct dependency. If a latest release cannot coexist with the project after documented migrations, stop and report the exact incompatibility before reducing scope.

## Verification

Run these checks after migration:

1. `npm ci` to prove manifest and lockfile consistency from a clean dependency install.
2. `npm run build` to validate TinaCMS generation, Astro compilation, Svelte components, Tailwind processing, static routing, and Pages output.
3. `npm outdated --json` to confirm no direct npm dependency remains outdated.
4. `npm audit` to identify remaining security advisories; fix actionable findings without unrelated dependency additions.
5. Review the final diff for unintended generated or content changes.

The project does not define format, lint, typecheck, or test scripts, so those checks are unavailable. Build success is the primary project-defined validation signal.

## Success Criteria

- Every scoped npm package resolves to the target latest release.
- CI uses Node.js 22 and the latest stable action majors listed above.
- `package.json` and `package-lock.json` are consistent.
- Clean install and production build pass.
- Existing site behavior and deployment configuration remain intact.
- Any unresolved audit advisory or environment-dependent Tina limitation is reported explicitly.
